Report: decisions and why

About this project

Air quality and wind in Iceland, for the Vefskólinn Module 4 guide "Connecting to the World". It combines live air quality from Loftgæði with live weather from Veðurstofa Íslands: a map of every air quality station coloured by the European Air Quality Index, a panel with one coloured bar per pollutant and the wind nearby, faint pollution clouds, and moving wind streaks.

  • Live site: connecting-to-the-world.onrender.com (free hosting on Render: after about 15 minutes without visitors it goes to sleep, and the first visit then takes up to a minute to load)
  • Source code: github.com/Oliverer9/connecting-to-the-world
  • Built with React and Vite for the page, Express for the server, and Leaflet for the map.

Most of the code was written by an AI coding agent (Claude Code), and this report was written by it as the guide asks, with every decision and the reason for it. GitHub Copilot in VS Code was the agent that used the MCP server and the skill. I tested the results and checked claims against the real data; where something was not verified, the report says so.

API, MCP server and skill: what's the difference?

API (Loftgæði, Veðurstofa)
How the website gets data. The server sends an HTTP request to an address such as api.vedur.is/weather/... and gets JSON back. It runs every time someone uses the site, with no AI involved.
MCP server (vedurstofa-mcp)
How the AI agent gets tools. It plugs into Copilot, not into the website, and gives the agent functions like get_weather_now that it can ask to run. The agent only asks; the MCP server runs the code, and I approve each call. It used the same Veðurstofa data while I was building.
Skill (verify-weather-data)
Instructions that change how the agent behaves. It is a Markdown file the agent loads when a question matches its description. It doesn't give the agent any new abilities, but it tells it how to use the ones it has: in this case, to check the time and the API before trusting a tool's answer.

In short: the API feeds the website, the MCP server gives the agent hands, and the skill gives the agent habits.

APIs

Loftgæði (air quality, Umhverfis- og orkustofnun) and Veðurstofa Íslands (weather observations). Wind decides whether pollution stays or blows away, so the two belong together. Both were tested live on 28.10.2026: both return 200, need no key and send Access-Control-Allow-Origin: *.

How they are combined

The two APIs number their stations differently, so there is no shared id. Both station lists have coordinates, so the server matches each air quality station to the nearest active weather station using the haversine distance. In testing every match was within 10 km.

Decisions

  • Fetch on the server, even though CORS would allow the browser. The join needs four requests (readings and station lists from each API); doing it once on the server keeps the page to one request and keeps the pattern ready for an API that needs a key.
  • Cache for 5 minutes. Weather updates every 10 minutes and air quality every hour, so calling both APIs on every page load would only add load on their servers.
  • Show every pollutant a station measures. Stations measure different things (dust, NO₂, SO₂, H₂S), and a fixed set left many stations empty.
  • Negative readings are shown as 0. Sensors read slightly below zero when there is almost nothing in the air.
  • Leave out stations that are not reporting, and weather stations that have closed (ending is not null) or have no wind reading.

Rate limits, keys and errors

  • No documented rate limits. Neither API's documentation mentions limits, quotas or terms, and neither sends rate-limit headers (checked 30.10.2026). That doesn't mean there are none, so the site is built to be polite anyway.
  • The 5-minute cache sets the load. However many people use the site, the server calls each API at most twice every 5 minutes (readings and station list), about 24 requests an hour per API. The data doesn't change faster than that: Veðurstofa updates every 10 minutes, and Loftgæði hourly at about 17 minutes past the hour.
  • No keys. Both APIs are open. The server is still set up to read keys from a .env file that is never committed, if a later API needs one.
  • Errors. Each request gives up after 8 seconds. If an API fails, the server logs the real error and sends the page a short, friendly message, which the page shows in place of the data.

Map and pollution levels

The site shows every air quality station on a map, coloured by how polluted the air is, and a separate panel for the chosen station with one coloured bar per pollutant.

Which scale for "how bad"

  • European Air Quality Index from the European Environment Agency, with six levels from Good to Extremely poor, based on hourly values of PM2.5, PM10, NO₂, O₃ and SO₂. The limits were copied from the EEA's own index page (airindex.eea.europa.eu), checked 29.10.2026, and live in server/airIndex.js.
  • Considered: loftgaedi.is's own scale. It only publishes numbers for SO₂, and that table is built for short volcanic gas peaks (10–15 minutes). It is much looser than the EEA scale ("Good" goes up to 350 µg/m³ against 20–40 in the EEA index). One scale for all pollutants was easier to read and compare.
  • Values between bands. The EEA writes the limits as whole numbers (PM2.5 0–5, 6–15…), so 5.5 doesn't fit anywhere. A value belongs to the first level whose upper limit it doesn't exceed, so 5.5 counts as Fair.
  • A station is as bad as its worst pollutant, which is how the EEA index works too.
  • H₂S, PM1 and CO have no level. The EEA index doesn't cover them. On 29.10.2026 nine stations only measured H₂S (mostly near geothermal areas), so they are grey and labelled "No index". Their values are still shown, but no colour is invented for them.
  • Colour is never the only clue. Each level name is written next to its colour in the legend, the bars, the dropdown and the marker tooltips. Markers and bars have a dark outline so the light colours stand out from the map and the background.

The map

  • Leaflet with OpenStreetMap tiles. Free, no API key and no account, and OpenStreetMap only asks for the attribution shown on the map.
  • Considered: CARTO's light basemap, whose pale grey would make the level colours stand out more. Tested it, and its tiles now only say "API KEY REQUIRED", so OpenStreetMap stayed. Older tutorials (and the AI's memory) still list it as keyless.
  • Scroll to zoom is on, and the map can be dragged up to half of Iceland's size past the coast in every direction, but no further (maxBounds). At first the limit was Iceland's own outline, which felt too tight. Zoom moves in half steps so the stations fill the box better.
  • Pollution clouds. Each station with a level gets a faint, blurred circle in its level colour, under the wind and the markers. It is 5 km in radius, as a hint of the area around the station, since a station only measures the air where it stands. Zoomed out, 5 km is only a few pixels and hid under the marker, so a cloud never gets smaller than 30 px across on screen. Stations with no index get no cloud, so no colour is made up for them.
  • The dropdown stays as another way to pick a station. Reykjavík's stations sit close together on the map, and a list is easier for screen reader users.

Wind animation

Inspired by the wind map on icelandweather.is, where moving streaks follow the wind measured right now. Wind is what moves pollution around, so it belongs on the same map as the air quality stations.

  • Uses the same Veðurstofa call the site already makes: the server now also sends wind speed and direction from every weather station (about 270), which added about 40 KB to the response.
  • From points to a wind field. The stations are spread over a grid covering Iceland. Each grid point gets a weighted average of the stations within 40 km, where closer stations count more (inverse distance weighting). Points with no station within 40 km get no wind, so no wind is invented far out at sea.
  • Direction. Veðurstofa gives the direction the wind comes from (166° means from the south-southeast), so the streaks move the opposite way.
  • Drawn on a canvas in its own map layer, between the map and the station markers, so it never covers or blocks the markers.
  • Hides while the map is dragged or zoomed, then starts again. The streaks are stored as screen pixels, which stop matching the map as soon as it moves.
  • Tried and reverted: wind that keeps moving during drag and zoom. A later version stored the streaks as map positions so they could keep flowing while the map moved. It needed several rounds of fixes (streaks jumping during Leaflet's zoom animation, stretching after a zoom, lagging while dragging), and a change to time-based speed made the streaks look worse. The first version looked best, so it was restored. Lesson: each fix was reasonable on its own, but the simpler version was the better product.
  • Can be turned off with a button (WCAG asks for a way to pause anything that moves for more than five seconds), and it starts off for people whose system asks for reduced motion.
  • Testing problem: the test browser was hidden, and hidden browsers don't run animations at all (0 frames per second). To check the drawing, the animation was run on a timer instead while testing. The reduced-motion setting couldn't be tested there.

What went wrong and how it was found

  • The map opened zoomed all the way in (zoom 17, no stations visible). Leaflet measured the map box before the layout had its final size, so fitting the stations zoomed to the maximum. Fixed by calling invalidateSize() before fitBounds().
  • The map still didn't load properly on my computer unless I zoomed in. It couldn't be reproduced in the test browser, so the fix had to cover the likely cause: the map box changing size after the map started, which Leaflet doesn't notice by itself. Now a ResizeObserver re-measures the map every time its box changes size, and the map always starts from a view of all of Iceland. Confirmed working on my computer afterwards.
  • Markers could be focused with Tab, but Enter did nothing. Leaflet makes markers into buttons but doesn't select them from the keyboard. Found by testing with the keyboard; fixed by handling Enter and Space.
  • The page was 27 px too wide on a phone because the dropdown grew to fit the longest station name. Fixed with max-width: 100%.

MCP server

vedurstofa-mcp v1.0.1 by sandsower (unofficial). It gives the coding agent six tools built on the same Veðurstofa data the site uses: current weather, forecasts, text forecasts, weather warnings, earthquakes and a station list. It runs locally over stdio and is connected to GitHub Copilot in VS Code through .mcp.json in this project. It plugs into the agent, not into the website. (It started in .vscode/mcp.json; during the project VS Code asked to migrate MCP settings to .mcp.json, the same file name other agents such as Claude Code use.)

Checked before running it

  • No install scripts. Three dependencies: the official MCP SDK, zod and node-html-parser.
  • The code only contacts vedur.is and api.vedur.is. It does not start other programs, write files or read secrets; the only environment variable it reads turns on debug logging.
  • It ships a certificate file. It is GlobalSign's real intermediate certificate (valid to May 2027), which vedur.is does not send itself. The server adds it to its own trusted list, so certificate checking stays on.
  • All six tools only read data.

Decisions

  • Pinned to version 1.0.1, the version that was read, so a later update can't run new code without anyone looking at it first.
  • Earthquakes tool: the course notes say get_earthquakes fails with 422 unless it is called with include_unreviewed: true.

Test: "What's the weather in Reykjavík right now?" (29.10.2026)

The chat only showed "Search Tools", not which tool answered. VS Code's own log shows the full sequence: Copilot searched its tools and found the six vedurstofa tools, started vedurstofa-get_weather_now, asked for permission, got approve-once, and the tool finished 0.6 seconds later. Permission was given once rather than for the whole workspace, so every new call has to be approved.

Skill

verify-weather-data, written for this project, in .agents/skills/verify-weather-data/SKILL.md (the folder VS Code reads skills from).

Why this skill

The MCP test above showed a real weakness: the tool reported an observation "from 23:00" at 22:39, Copilot noticed the problem in its own reasoning, and still told the user "Observed at 23:00". The skill targets exactly that. It tells the agent to:

  1. find out the current time (UTC, which Iceland uses all year);
  2. get the data;
  3. treat any "observation" from the future as a forecast or a mistake, and say how old stale data is;
  4. check one value against Veðurstofa's or Loftgæði's API directly;
  5. answer with units, station, time and source, plus a Checks line, and never leave out a problem it noticed.

How it is built

  • The description decides when it is used. Copilot only reads the name and description until a question matches; then it loads the rest. So the description names the situations (current weather, wind, temperature, air quality in Iceland) and the tools and APIs (vedurstofa MCP, api.vedur.is, api.ust.is).
  • Short and concrete: 64 lines, with the exact API addresses and field names, so the agent doesn't have to guess them (the course warns that agents remember old, dead APIs).
  • An example answer showing the 23:00 case handled correctly.

Before and after

Before (no skill, 29.10.2026): see the MCP test above. The impossible time was reported as fact, and nothing was checked against the API.

After (with the skill, 30.10.2026 at about 00:20 UTC), same question in a new Agent chat:

  • The first step in the chat is "Read skill: verify-weather-data", so Copilot matched the question to the skill's description and loaded it. It then stated the skill's plan (check the UTC time, fetch the reading, cross-check with Veðurstofa's API) and ran the PowerShell time command from step 1.
  • Copilot asked to use the vedurstofa tool and then to fetch api.vedur.is directly. It didn't do that check before the skill.
  • It gave the station, the observation time in UTC, the source, and how old the reading was ("about 1 minute old as of 00:20:46 UTC").
  • Its Checks line said the MCP tool reported 01:00 UTC, "which is in the future relative to the current time, so that observation timestamp was disregarded", and that the API reading was used instead.
  • Before the skill, Copilot noticed the impossible time only in its hidden reasoning and left it out of the answer. This time the problem is in the answer itself, which is what the skill's "never leave out a problem you noticed" rule is for.
  • Verified independently: the API's newest Reykjavík reading at 00:27 UTC was 00:20, 5.12 °C, 3.08 m/s from SE (137°), gusts 4.51 m/s, humidity 84 %, pressure 1003.88 hPa. Every number in the answer matches.

What this showed about the MCP server

The future timestamp happened twice: "23:00" at 22:39 and "01:00" at 00:20. Both times it was the next whole hour, so it looks like a real bug in vedurstofa-mcp's get_weather_now (perhaps rounding the time up, or labelling an hourly value by the end of its hour), not a one-off. That would be worth reporting to the project on GitHub. The skill doesn't fix the tool, but it stops the agent from passing the wrong time on.

What the AI got wrong, and how it was caught

The guide asks about the limits of AI-generated code. These are the times the AI (or a tool it used) was wrong or unsure, and what showed it:

  • Out-of-date knowledge: CARTO's basemap was used as "keyless", but its tiles said "API KEY REQUIRED". Caught by looking at the result.
  • A tool giving wrong data: the vedurstofa MCP server reported observation times from the future, twice. Caught by comparing with the API directly, then handled with a skill.
  • Code that worked in one test but not another: the map loaded properly in the AI's test browser but not on my computer. Caught by testing on my own screen. Map markers could also be reached with Tab but not chosen with Enter, which the AI caught by testing with the keyboard.
  • Fixes that made it worse: the wind animation went through several "improvements" that I didn't like, and the first version was restored.
  • Its own claims: while writing this report, the AI first wrote that Copilot's reasoning had noticed the wrong time in the skill test. The screenshot didn't show that, so the sentence was changed to what the evidence shows.

Not verified

  • The wind animation starting switched off for people who ask their system for reduced motion. The test browser couldn't emulate that setting.
  • How the site behaves if one of the APIs is down for a long time; only the error path in the code was checked, not a real outage.
  • The exact colours of the European Air Quality Index levels. The EEA page gives the limits but not the colour values, so the colours follow its order (blue-green to purple) rather than its exact palette.
